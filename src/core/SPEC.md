# core — spec

The contract every command, plugin, and protocol adapter is built on. This
module defines *how a command is described and invoked*; it deliberately knows
nothing about HTTP, MCP, or CLI specifics — those live in their own adapters
(see [`http/SPEC.md`](../http/SPEC.md), [`mcp/SPEC.md`](../mcp/SPEC.md), `cli.ts`).

## Files

| File | Responsibility |
|---|---|
| `types.ts` | `TavernaContext`, `CommandDef`, `RegisteredCommand`, `CommandRegistry`, `JsonSchema`, `Protocol` |
| `vault-commands.ts` | "vault" command group: `get_projects`, `get_project`, `get_inbox`, `get_backlinks` |
| `task-commands.ts` | "tasks" command group: `get_task_status`, `archive_task`, `add_task`, `create_project` |
| `flow/` | "movement" command group + the canvas-driven flow engine — see [`flow/SPEC.md`](flow/SPEC.md) |
| `index.ts` | `coreCommands` — the populated `CommandRegistry` every adapter reads from |

## `CommandDef`

```ts
interface CommandDef {
  id: string
  description: string
  params?: JsonSchema          // JSON Schema, not Zod — see "Why JSON Schema" below
  expose?: Protocol[]          // omitted → all protocols; [] → none
  handler: (params: Record<string, unknown>, ctx: TavernaContext) => Promise<unknown>
}
```

- `params` is a plain JSON Schema object (`Record<string, unknown>`), validated
  at invocation time with `ajv` (`{ allErrors: true, strict: false }`). This is
  the schema every adapter derives its transport-specific input shape from
  (HTTP query/body, MCP `inputSchema`, CLI `--flags`).
- `expose` is the *only* protocol-specific field a command declares. It exists
  purely to opt out (e.g. an internal command that shouldn't be reachable over
  HTTP). Everything else — paths, tool names, CLI subcommand structure — is
  generated by convention (see the root [`SPEC.md`](../../SPEC.md)).
- Handlers receive raw, already-validated `params` and a `TavernaContext`; they
  never see the transport. A handler that needs to know "am I running over
  HTTP?" is a sign the abstraction has leaked — fix the command, not the adapter.

### Why JSON Schema, not Zod

Commands must be describable in a transport-agnostic, serializable form: HTTP
needs to publish `/api/config/schema`, MCP needs an `inputSchema` to hand the
client, and both are naturally JSON Schema. A Zod shape would force every
adapter to either depend on Zod or convert it — JSON Schema is the lowest
common denominator all three protocols already speak natively.

## `TavernaContext`

```ts
interface TavernaContext {
  config: TavernaConfig
  notificationBus: NotificationBus
  prompt?: (field: string) => Promise<string>
}
```

The single object threaded through every handler and plugin hook. `prompt` is
optional and CLI-flavored: it's how the flow engine asks for a required field
it couldn't resolve any other way (see [`flow/SPEC.md`](flow/SPEC.md)). Adapters
that can't prompt interactively (HTTP, MCP) simply omit it — missing fields
then surface as a normal command error instead of hanging on stdin.

## `CommandRegistry`

A flat list of `RegisteredCommand` (a `CommandDef` plus an optional
`namespace`). Core commands register with no namespace; plugin commands
register under the namespace derived from the plugin (see
[`plugin/SPEC.md`](../plugin/SPEC.md)).

- `find(namespace, id)` / `list()` / `listFor(protocol)` — lookups. `listFor`
  is what every adapter iterates to generate its routes/tools/subcommands; it
  filters by `expose` (a command with `expose` omitted matches every protocol).
- `execute(namespace, id, params, ctx)` — the **only** way a command should
  ever be invoked. It validates `params` against the JSON Schema with `ajv`,
  calls the handler, and normalizes the outcome to `{ data }` or `{ error }`.
  Adapters never call `handler` directly — this guarantees validation and error
  shape are identical across HTTP, MCP, and CLI.

`namespace + id` is the registry's identity key — two commands with the same
`id` can coexist as long as their namespaces differ (core has no namespace, so
a plugin can't accidentally shadow a core command by reusing its `id`).

## Command groups (spec 1)

Core commands are organized into three groups, each in its own file/module:
**vault** (read-only vault queries), **tasks** (task/project mutation), and
**movement** (flow transitions, in `flow/`). This grouping is purely
organizational — the registry is flat, and nothing depends on group membership
at runtime. New groups should follow the same pattern: a file exporting handler
functions plus a `CommandDef[]`, wired into `coreCommands` in `index.ts`.

## Evolution notes

- Adding a command never requires touching an adapter — write the `CommandDef`,
  push it into `coreCommands` (or a plugin's `commands`), and it's
  automatically live on every protocol it's exposed to.
- Keep handlers free of protocol assumptions and free of user-specific
  concepts (see the root spec's "specs stay abstract" note) — anything
  user-specific belongs in a plugin or in vault configuration.
- If a new cross-cutting per-command property feels necessary (the way `expose`
  is), ask whether it can instead be derived from `id`/`description`/`params`
  by convention — that's kept the adapters and the registry free of special cases
  so far (see the `get_*` → `GET` convention in the HTTP adapter).
